## 重点

- 4.2 数据访问协议 (Locking Protocol)

#### 1. 概述 (Introduction)
*   **并发 (Concurrency):** 指 DBMS 允许许多事务在**同一时间**访问同一个数据库。
*   **并发控制机制 (Concurrency Control Mechanism):** 用于确保并发事务之间互不干扰，防止数据不一致。

---
#### 2. 核心概念对照表 (Core Concepts Mapping)

| 英文术语                        | 中文术语         | 定义与说明                                      |
| :-------------------------- | :----------- | :----------------------------------------- |
| **Concurrency**             | 并发           | 多个事务同时执行。                                  |
| **Lost Update**             | 丢失修改         | 一个事务的更新覆盖了另一个事务未提交的更新。                     |
| **Uncommitted Dependency**  | 未提交依赖/读“脏”数据 | 一个事务读取或更新了另一个事务**尚未提交 (Uncommitted)** 的数据。 |
| **Inconsistent Analysis**   | 不一致分析/不可重复读  | 事务读取数据后，该数据被另一事务修改，导致再次读取时值不同。             |
| **Exclusive Lock (X Lock)** | 排他锁/写锁       | 若事务持有某数据的 X 锁，其他事务无法申请任何锁（写独占）。            |
| **Shared Lock (S Lock)**    | 共享锁/读锁       | 若事务持有某数据的 S 锁，其他事务可申请 S 锁但不能申请 X 锁（读共享）。   |
| **Deadlock**                | 死锁           | 两个或多个事务同时处于等待状态，互相等待对方释放锁。                 |
| **Serializability**         | 可串行性         | 并发执行的结果与某种串行执行（一个接一个）的结果相同，即被认为是正确的。       |
| **Schedule**                | 调度           | 一组事务的执行序列（可以是串行或并发交错的）。                    |
| **Two-Phase Locking (2PL)** | 两段锁协议        | 事务必须在释放任何锁之前获得所有需要的锁，保证调度可串行化。             |

---
#### 3. 三大并发问题 (Three Concurrency Problems)

如果没有并发控制，可能会出现以下三种异常情况：

1.  **丢失修改 (The Lost Update Problem):**
    *   两个事务读入同一数据并修改，其中一个事务的修改被另一个事务的修改覆盖了（例如：T1将A从10改为8，T2将A从10改为9，最后结果是9，T1的修改丢失）。
2.  **未提交依赖 / 读“脏”数据 (The Uncommitted Dependency Problem):**
    *   事务 A 读取了事务 B **已更新但尚未提交**的数据。如果 B 后来回滚了，A 读取的数据就是无效的（脏数据）。
3.  **不一致分析 (The Inconsistent Analysis Problem):**
    *   当一个事务在进行聚合计算或分析时，另一个事务修改了数据，导致分析结果不一致,。

#### 4. 封锁机制 (Locking)

##### 4.1 锁的类型与相容性
*   **X 锁 (写锁):** 独占。如果有 X 锁，拒绝其他任何 X 或 S 锁请求。
*   **S 锁 (读锁):** 共享。如果有 S 锁，拒绝 X 锁请求，但**允许**其他 S 锁请求。
*   **相容矩阵 (Compatibility Matrix):**
    *   X 与任何锁都不相容。
    *   S 仅与 S 相容。

##### 4.2 数据访问协议 (Locking Protocol)

1.  **读操作:** 必须先申请 **S 锁**。
2.  **写/更新操作:** 必须先申请 **X 锁**。如果已持有 S 锁，必须将其**升级 (Promote)** 为 X 锁。
3.  **等待机制:** 如果请求被拒绝（因冲突），事务进入**等待状态 (Wait State)**，直到锁被释放。
4.  **锁的释放:**
    *   X 锁必须持有至事务结束 (COMMIT 或 ROLLBACK)。
    *   S 锁通常也持有至事务结束。

*注：封锁解决了“丢失修改”问题，但引入了新问题——**死锁**,。*

---
#### 5. 死锁 (Deadlock)

*   **定义:** 两个或多个事务同时处于等待状态，每个都在等待“别人”释放锁，形成循环等待。
*   **检测 (Detection):** 系统通过检测 **等待图 (Wait-For Graph)** 中的**环 (Cycle)** 来发现死锁,。
*   **解决 (Breaking):** 选择一个死锁事务作为 **受害者 (Victim)** 进行回滚 (Rollback)，释放其占用的锁，让其他事务继续运行。

---
#### 6. 可串行性 (Serializability)

这是判断并发调度是否“正确”的标准。

*   **定义:** 如果一个并发调度（Interleaved Schedule）的执行结果，与这组事务在**某种串行顺序**（一个接一个运行，无交错）下的执行结果**完全相同**，则该调度是**可串行化的 (Serializable)**。
*   **正确性:** 可串行化的调度被认为是正确的调度。
*   **判定逻辑:**
    *   单个事务被认为是正确的（将数据库从一致状态转为另一一致状态）。
    *   串行执行是正确的（因为事务间独立）。
    *   因此，等价于串行执行的并发调度也是正确的。

---
#### 7. 两段锁协议 (Two-Phase Locking Protocol - 2PL)

如何保证调度是可串行化的？遵守 **2PL**。

*   **规则:**
    1.  **扩展阶段 (Growing Phase):** 事务在操作数据前必须获得锁。
    2.  **收缩阶段 (Shrinking Phase):** 一旦事务释放了**任何**一个锁，它就**不能再申请**任何新的锁。
*   **定理:** 如果所有事务都遵守两段锁协议，则所有可能的并发调度都是**可串行化**的。
